**启动顺序**：先 aibridge，再 xiaozhi-server。**入口务必是 `run-server.js`**（`index.js` 只是插件模块，直接 `node index.js` 会立即退出，属正常）。

**健康检查**：
```
curl http://127.0.0.1:8003/health        # {"status":"ok",...,"devices":N}（N = 当前在线连接数）
curl -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3300/   # 有响应即 aibridge 在线
```

> **重启必须验到底**（代码改动只能靠重启生效，`ConfigLoader.reloadConfig()` 无调用方）：`kill`（SIGTERM）对本服务**常常退不干净** —— 实测会先释放监听端口、但进程卡在优雅关闭里继续存活（STAT `SN`）并保留已建立的设备 socket，于是设备连着这个"半死"旧进程、新代码又没加载，看起来就是"修了但没生效"。标准流程：
>
> ```
> pkill -f run-server.js; pkill -f "npm start"
> sleep 3; ps -eo pid,stat,command | grep run-server.js   # 必须为空，否则 kill -9 <PID>
> nohup npm start >> logs/server.out 2>&1 &
> curl -s http://127.0.0.1:8003/health                   # devices 应等于已开机板数
> ```
>
> 另外：`lsof -iTCP:8003 -sTCP:LISTEN` 只看 PID 是否唯一，端口释放不等于进程退出，两者要分开验。

## 2. 唤醒与基本对话

- 识别用阿里云 `qwen3-asr-flash`，回复用 gemma4:31b，语音用 Edge TTS。
- 设备屏幕状态：`待命`(STANDBY/Idle) → `倾听中`(Listening) → `说话中`(Speaking)。

**唤醒词按板型不同，服务器侧不可改**（编译期写死）：

| 板 | 唤醒词 | 实现 |
|---|---|---|
| 鹿小班 | `你好小智` | AFE WakeNet `wn9_nihaoxiaozhi_tts`，无 Multinet 命令词（`SR_MN_CN_NONE`） |
| 大酒桶 | `大酒桶启动` | `CONFIG_USE_CUSTOM_WAKE_WORD="da jiu tong qi dong"`（阈值 20）+ `SR_MN_CN_MULTINET7_QUANT` |

鹿小班换不成自定义词：8MB 布局下 assets 分区（2M）实际只剩约 314KB、app 只剩约 193KB，装不下自定义 WakeNet 模型（通常几百 KB～1MB）。大酒桶能装是因为 16m.csv 的 assets 分区更大。

## 3. 打断规则（重要）

本板**无 AEC 回声消除**，麦克风会收进喇叭自己的播放声。因此：

| 打断方式 | 是否支持 | 说明 |
|---|---|---|
| 说话时再喊唤醒词 | ✅ 支持 | 显式打断，设备发 abort、停止当前播报并重新监听 |
| 按 BOOT 物理按键 | ✅ 支持 | 同上，最可靠的打断方式 |
| 直接开口盖过它说话 | ❌ 不支持 | 服务端**故意不做**"检测到人声就立即打断"——否则回声会自杀式打断每一轮回复 |

若发现"喊唤醒词也打不断"，多为麦克风未采集到声音，参见第 10 节板型问题。

## 4. 语音三态模式（聊天 / 办公 / 休息）——操作口径

转换的完整规则见第 5 节，本节只留"怎么操作、改哪里"。

指令触发词在 `config.json` 的 `modeKeywords` 里配置（归一化全等匹配，去掉空格标点后比对）：
```
modeKeywords: { employeeOn[], employeeOff[], restOn[], restOff[], practiceOn[], practiceOff[] }
```
- 默认休息触发词含："休息吧 / 你休息吧 / 你去休息吧 / 进入休息模式"等。
- **生效方式**：经前台/API 改是热生效；手工改磁盘 `config.json` 必须重启（原因见 5.8.2）。
- 休息模式：设备进入待命（清"倾听中"），**WebSocket 保持不断开**，仍可用唤醒词唤醒；退出用 `modeKeywords.restOff` 里的词。

- **开机默认进入休息**：设备 hello 握手时，服务端把「开机第一次连接」也当作休息态处理——即使 `resting` 列为 0，也会置 `restMode=true`、写 `resting=1` 并下发 `sleep`+待机 layout，屏幕表现与语音口令进入休息完全一致，不再出现「聊天/待命」残影（[websocket.js:533-589](file:///Users/fengleiren/git/xiaozhi-server/core/handlers/websocket.js#L533-L589)）。例外：`server1`（移动热点备用，无登录态）保持原行为不下发。

三态互斥：进入任一新模式会先退出旧模式并**全量重推 mode 标签**。进入办公模式时若已在休息态，服务端先发 `wake` 解除待机，再发 `tts` 问候，保证设备退出待机后再播。

- **模式寻址（只对目标设备生效）**：指令句里点名即可——匹配到设备 `name`（配置页可改，默认=MAC 前缀，存 `xz_devices.name`）或 MAC（口语写法 `10:51:..`/`1051db721368`）就只对该设备进入/退出该模式；点名优先于全局。
- 员工模式退出词：`退出员工模式` / `退出办公模式` / `员工模式退出` / `办公模式退出`（数字员工侧另有 `退出工作` / `工作退出` / `下班` / `结束面试` / `面试结束` / `结束接单` / `接单结束`）。
- **远程唤醒（不靠语音词）**：外部系统/前端可直接 `POST /api/wake {"device_id":"<MAC>","broadcast":"带名播报内容"}`（`X-Xiaozhi-Key` 用 `voiceFlow.token`）→ 服务端置 `restMode=false`、清 `xz_devices.resting`、下发 `wake` + 解除 i18n 覆盖，并回 `chat` 问候（[broadcastRoutes.js:27-45](file:///Users/fengleiren/git/xiaozhi-server/core/routes/broadcastRoutes.js#L27-L45)）；固件 `SetRestMode(false)` 后，后续任何 `SetStatus` 自动恢复默认「待命」。设备侧 MCP `self.rest` 走同一路径。
- **心跳自愈**：服务端每 30s 幂等重发 `mode` 标签（休息态同时重发 i18n 覆盖，[websocket.js:2023-2041](file:///Users/fengleiren/git/xiaozhi-server/core/handlers/websocket.js#L2023-L2041)）；若设备屏上「待命」压过「休息」，最多 30s 自愈；若整个标签丢了（设备被判为新会话），需重新 hello（重连/重唤醒）才会重发。

## 5. 设备状态与模式转换（权威规则）

「设备状态之间如何转换」的唯一权威说明，服务端与固件两侧规则集中在此，不要在其他章节另行描述。

### 5.1 三层模型（先分清层，再谈转换）

| 层 | 归属 | 取值 | 权威方 |
|---|---|---|---|
| **L1 设备状态 DeviceState** | 固件 | Unknown / Starting / WifiConfiguring / AudioTesting / Activating / Upgrading / Idle / Connecting / Listening / Speaking / Notifying / FatalError | **固件**（严格状态机，服务端不能直接改） |
| **L2 业务模式 mode** | 服务端会话 | 聊天 chat / 员工 employee / 口语 practice / 休息 rest /（开发 dev） | **服务端**（固件只被动接收 `mode` 标签文本） |
| **L3 屏幕表现** | 固件渲染 | 模式栏 mode_label、状态栏 status_label、表情/待机图 | 由 L1（状态栏）+ L2（模式栏、休息覆盖）共同决定 |

关键结论：**休息不是 L1 的一个状态**。休息 = L1 保持 `Idle` + L2 打上 rest 标记 + L3 显示「休息/休息/睡觉脸」。所以休息态下设备依旧在线、可被服务端推送。

### 5.3 L2：服务端业务模式

**取值优先级与互斥** —— `_sendMode` 的取键顺序（[websocket.js:2332-2345](file:///Users/fengleiren/git/xiaozhi-server/core/handlers/websocket.js#L2332-L2345)）：

```
restMode > practiceMode > employeeMode > (devMode 总开关 → dev) > chat
```

- `rest-on` 同时置 `employeeMode=false`（互斥，休息优先）
- `practice-on` 同时置 `employeeMode=false`
- 待命不是一种模式标签（已并入聊天）

**持久化** —— `xz_devices.resting` 列（迁移与写入：[store.js:84-87](file:///Users/fengleiren/git/xiaozhi-server/core/managers/store.js#L84-L87)、[store.js:259-266](file:///Users/fengleiren/git/xiaozhi-server/core/managers/store.js#L259-L266)），设备一览据此显示「休息」而非「离线」（[deviceRoutes.js:375-377](file:///Users/fengleiren/git/xiaozhi-server/core/routes/deviceRoutes.js#L375-L377)）。

**在线判定口径** —— 一律「连接在就在线」：`DeviceModel.isOnline()` 以 `connection.readyState === OPEN` 为准（无连接引用时才退回状态位 + 活动窗口），见 [device.js:47-57](file:///Users/fengleiren/git/xiaozhi-server/core/models/device.js#L47-L57)。设备一览（`/api/devices/known`）、放送/唤醒（`getBroadcastTargets`）、`/api/voice/devices`、`/health` 四个出口共用该口径，不存在「设备端明明连着、后台显示未在线」的空间。休息态下 `lastActivity` 长期不刷新属正常（无有效语音），不得用它判活。

### 5.7 已知陷阱（都已在代码里修复，回归时逐条验）

1. **休息态周期性漂回「聊天/待命」**：固件 120s 下行超时 + NAT ~60s 掐静默 TCP → 重连被当新会话。解法是 5.6 的 30s 心跳，不要靠改固件。
2. **重连后设备工具消失**：旧连接迟到的 close 事件按同一 clientId 清掉了新登记的 MCP 客户端。解法是断开清理做连接归属校验（[mcp.js handleDeviceDisconnect](file:///Users/fengleiren/git/xiaozhi-server/core/services/mcp.js)）。
3. **开机闪「聊天」**：模式栏曾硬编码初始文案，现改为空字符串。
4. **休息画面闪四段**：`ShowStandby` 取图优先级颠倒，现按 5.5 顺序。
5. **状态栏「休息」显示成方块**：状态栏未用 `font_mode_20_4` 扩展字体。
6. **休息中的设备在后台显示「未在线」**：`isOnline()` 曾用 `lastActivity` 的 2 分钟活动窗口判活，而 `lastActivity` 只在注册时写一次（`updateDeviceStatus`/`updateDevice` 无调用点），于是连上 2 分钟后必判离线。现改为连接 readyState 判活（见 5.3 的「在线判定口径」）。另：`/health` 曾把 Map 当普通对象做 `Object.keys().length`，恒报 0。
7. **休息后首次开口先播一句依依不舍的告别语**：休息态仍走保活音频帧 → `_checkIdleTimeout` 按 120s 无语音触发 `end_prompt`；口语练习态早有豁免而休息态没有。现补 restMode 豁免 + 休息期间滑动空闲时钟（只豁免不滑动，会把冻结的时间戳留给退出休息后的第一帧，实测 97ms 后就播出告别语），并把 `closeAfterChat` 改成有人声即复位（原先一旦置位永不复位）。
8. **设备明明连着、设备一览却显示离线**：固件重连沿用同一个 ClientID，旧连接**迟到的 close 事件**会按 clientId 主键把新连接刚登记的在线记录一并删掉（`DeviceManager.removeDevice(clientId)` 无归属校验），DB 也被顺手标离线。解法是 `handleConnection` 用 `activeConnections` 记当前活跃连接，`handleDisconnect` 只有命中该对象才做设备层清理与离线持久化（[websocket.js:105-106](file:///Users/fengleiren/git/xiaozhi-server/core/handlers/websocket.js#L105-L106)、[websocket.js:217-236](file:///Users/fengleiren/git/xiaozhi-server/core/handlers/websocket.js#L217-L236)），与陷阱 #2 的 MCP 守卫同源。**加完守卫必须重启**：守卫在磁盘上而进程是守卫之前启的，同样照旧误删（实例：日志先打 `设备移除`、而设备侧 TCP 仍 ESTABLISHED 且 ping 得通）。

9. **休息中的两个真相会分岔**：设备端 `rest_mode_` 是显示态、活过 WS 重连；服务端 `ws.restMode` 是**每条连接各自**的标记，靠 hello 时统一置真（入口 1）来对齐。二者一旦错开（如服务端进程重启后未走到入口 1，或固件镜像早于源码修改），被动放送的 `listen:"disable"` 与睡觉脸恢复就会表现不一致。**排查口诀**：先看服务端日志有没有 `💤 休息中收到被动放送，保持休息态` 与放送后是否冒出 `listen start`（有 = 被拉进倾听，休息态被真实交互清掉）；再看**屏幕表现**，那一段取图逻辑在固件（`lcd_display.cc ShowStandby` + `application.cc HandleStateChangedEvent`），源码改动未重烧就不会生效。

## 6. 时间 / 主备容灾 / 错误兜底

### 6.1 设备时间
- 设备时间来自 **OTA 下发的 `server_time`**（非 SNTP）。
- `timezone_offset` 单位是**分钟**（日本 UTC+9 = 540）。服务器已按本机时区自动换算下发。
- 若要固定时区：在 `config.json` 的 `server` 里加 `"timezone_offset": <小时数>`（如 9，可 0/负值）。
- 改了时间相关后，需让设备**重新走一次 OTA**（唤醒重连或断电重启）才刷新显示。

## 7. 语音通道与外部系统对接

把口语练习 / 面试的作答改由小智 ESP32 设备语音收发时，xiaozhi-server 只承担**两个 flow-agnostic（不认业务域）的原语**：下行 `speak`（把文本推给指定设备播报）、上行 `session`（设备进入"作答采集"态，说完把聚合转写 POST 回发起方回调）。流程、出题、评分、轮次一律留在控制器（aistudy / aiinterview）。

> 控制器侧的接法与端到端步骤见：aistudy `docs/xiaozhi-voice.md`、aiinterview `docs/xiaozhi-voice.md`。

### 7.1 契约（`index.js` setupRoutes，端口默认 `:8003`）

| 端点 | 入参 | 成功返回 | 失败 |
|---|---|---|---|
| `POST /api/voice/speak` | `{deviceId, text}` | `{ok:true, accepted:true, devices:N}`（异步排队播报；**休息中的设备保持休息**，见 5.3 入口 7） | 400 空文本 / 404 设备不在线 |
| `POST /api/voice/session` | `{deviceId, endOn:'button'\|'auto', callbackUrl, sessionId, callbackToken?}` | `{ok:true, applied, deviceId, endOn}` | 400 callbackUrl 非法/不在白名单 / 404 设备不在线 |
| `POST /api/voice/session/close` | `{deviceId}` | `{ok:true, closed, deviceId}` | — |
| `POST /api/voice/devices` | `{}` | `{ok:true, devices:[{deviceId, clientId, name}]}` | — |

- **鉴权**：四端点均校验 `X-Xiaozhi-Key == config.voiceFlow.token`；密钥未配置 → 503（不裸跑），不符 → 401。
- **收卷回调体**（xiaozhi → 控制器）：`POST <callbackUrl>`，body `{deviceId, sessionId, transcript}`，携 `X-Xiaozhi-Key`（= 注册时的 `callbackToken`，缺省回落 `voiceFlow.token`）。
- **endOn 语义**：`button`=说完长按键收卷（qa/retell/面试这类长段讲述）；`auto`=每片段静音 VAD 判定收卷（跟读单句）。收卷复用既有 `practiceBuffer` + `listen stop`/auto-DONE，仅新增去域化的 `flowCollect` 分支把 `transcript` 吐给回调，**不跑教练总结、不播报**。

### 7.2 配置（`config.json`）

共享密钥只在顶层 `sharedToken` 定义一次；`voiceFlow.token` 与 `externalSystems.*.token` 一律写 `"$shared"`，启动时由 `core/utils/sharedToken.js` 解析（也支持 `"env:VAR"` 从环境变量注入，密钥不落盘）。外界系统统一登记在 `externalSystems`，启动时由 `core/utils/externalSystems.js` 编译为运行期的 `config.employee` / `config.voiceFlow` 视图（形状不变，消费方零感知）。

```jsonc
"sharedToken": "<共享密钥，须与 aistudy XIAOZHI_VOICE_TOKEN / aiinterview config.xiaozhi.voiceToken 同值>",
"voiceFlow": {
  "token": "$shared",
  "callbackAllowList": ["127.0.0.1", "localhost", "192.168.1.55", "ai.fsr.co.jp"]
},
"externalSystems": {
  "aiinterview": {
    "baseUrl": "http://127.0.0.1:30005",         // xiaozhi 主动调用（员工模式 employee-turn）的目标
    "token": "$shared",
    "inbound": ["voiceFlow", "broadcast"],        // 允许它使用的入站能力组
    "outbound": { "employeeTurn": { "path": "/api/xiaozhi/employee-turn", "timeoutMs": 90000 } }
  },
  "aistudy": {
    "token": "$shared",
    "inbound": ["voiceFlow"],
    "outbound": { "flowCallback": { "host": "127.0.0.1", "port": 3007 } }  // 仅登记收卷回调 host 到白名单
  }
}
```
能力组是封闭枚举（`core/utils/externalCapabilities.js`：入站 `voiceFlow`/`mcpCallTool`/`broadcast`，出站 `employeeTurn`/`flowCallback`），新增对接方只登记条目、不改公共层。`callbackAllowList` = 显式列表 ∪ 各系统 `outbound.flowCallback` host（只增不减）；按 host / origin / `.suffix` 精确匹配，空白名单拒绝一切回调（SSRF 防护）。注意：收卷回调 URL 本身仍由控制器在 `/api/voice/session` 请求体里逐次给出，注册表只登记其 host 到白名单，不充当回调地址源（控制器权威不变量）。

除手改 `config.json` 外，这套配置也可在管理界面 **Firmware Studio → 接口管理**（`/firmware/`，需 `manage.password` 登录）在线维护：`sharedToken`、回调白名单、`externalSystems` 增删改，保存时写回同一份 `config.json`（先备份 `.bak`、原子替换）并调用 `channel.reloadInterfaces()` 就地重解析/重编译，无需重启。写侧对能力名/方向/缺 `baseUrl` 做 fail-closed 校验（非法直接 400，不落盘）。

> 关键前提：下行 `speak` 依赖设备 WS 保活（"温和休眠 keepalive"）。若设备缩了 WS 则收不到播报，须先唤醒/确认在线。

### 7.5 端到端顺序（建议）
1. 起 xiaozhi-server → `smoke-voice.mjs` 看设备在线；空列表先解决保活。
2. `--device ... --text ...` 听设备出声，坐实下行通道。
3. 再进控制器端到端（aistudy 口语三档、aiinterview 面试到总分）；上行采集（VAD 聚合 + 按键 `listen stop`）只有真设备能验。

### 7.6 常见问题
- `404 设备不在线或未找到`：deviceId 不在 `/api/voice/devices` 列表 / 设备未保活。
- `400 callbackUrl 不在 callbackAllowList 内`：控制器回调 host 未登记，补 `callbackAllowList`。
- `503`：`voiceFlow.token` 未配置。
- 收卷后控制器没收到回调：查 xiaozhi 日志 `_postFlowCallback` 的告警；确认网络可回访控制器 `callbackBase`。

## 8. MasterPi 机器人动作类型

> 供查看/取舍用。本表与代码单一真源保持一致：
> - 服务端目录：`core/services/robotActions.js`（设定页与 `/api/robot/action-types` 均读它）

### 8.1 动作类型（22 类）

| id（装载键） | 名称 | 分类 | 语义参数 | 真机接线 | 会动硬件 | 说明 / 安全 |
|---|---|---|---|:---:|:---:|---|

| `robot_play_music` | 播放音乐 | 声音 | `keyword`：歌名/歌手搜索词 | ⏳ 未接线 | ❌ | 播放器尚未接线 |
| `robot_stop_music` | 停止音乐 | 声音 | 无 | ⏳ 未接线 | ❌ | 随播放器一同尚未接线 |
| `robot_take_photo` | 拍照识别 | 感知/问答 | 无 | ⏳ 未接线 | ❌ | 云台拍照，用于"看看这是什么"类问答；属**感知查询**，不是"动作" |
| `robot_search_face` | 人脸搜寻巡视 | 感知/问答 | `max_scan_sec`：扫描上限秒数（5~25，默认20） | ✅ | ✅ | 舵机扫描（s1躯干/s3颈/s6头）上下左右巡视 + DNN(YuNet) 人脸检测（替代 Haar，对印刷/卡通脸误报大幅降低）；命中即**开环扫描对准人脸**（相机为云台/头部安装：每轮**先扫头 s6 做水平、再扫颈 s3 做垂直收尾**——云台 pan 会耦合影响竖直，故垂直必须最后落子；实测 s6 对画面水平增益强、躯干 s1 几乎无增益，各取画面最居中档，多帧中位数，最多两轮细化，把脸拉到正中）+**蜂鸣+停止**；命中后端侧上报 `face_found` 事件，由 **server 统一调度**播报（反查 `settings.robot.body` 绑定的在线小智语音设备，按该设备语言播报固定文案 `faceFound`）；vision 类不做极短确认；**绝不碰轮子**。摄像头走 `/dev/v4l/by-id` 稳定链接自动定位；若派上 MJPEG 预览（`vision_stream.py`）在运行，search_face 会自动**借用预览流的检测框+嵌入**（`/frames` 端点，单路相机与预览共存），未运行则回退本地开相机。**检测+识别**：对准后 SFace（`cv2.FaceRecognizerSF`）取 128 维嵌入比对派上人脸库 `faces.json`，命中返回 `person`（称呼）与 `person_id`（库内稳定编号），陌生/未登记返回 `person=null`（距离超阈值 0.363）；舵机值域/增益详见 [`masterpi/doc/SERVOS.md`](../masterpi/doc/SERVOS.md) |
| `robot_get_battery` | 电池电压读取 | 传感器 | 无 | ✅ | ❌ | `board.get_battery` 读原始电压（mV 口径），用于低电提醒/状态上报；不运动；结果需被大模型**读出** |
| `robot_get_distance` | 超声波测距 | 传感器 | 无 | ✅ | ❌ | I2C 超声波（`Sonar.getDistance`，地址 0x77）测前方障碍物距离（cm）；**本机未接该模块时会优雅返回 `clear=false`**；不动车；结果需读出 |
| `robot_set_rgb` | RGB 状态灯 | 灯光 | `color`（预设名/#RRGGBB）+ `index`（both/left/right） | ✅ | ❌ | 走厂商**串口 `board.set_rgb`**（非 I2C）驱动两盏 RGB，状态/情绪可视化反馈；不动车 |
| `robot_color_detect` | 颜色识别 | 感知/问答 | `timeout_sec`（0.5~5，默认2） | ✅ | ❌ | 纯相机按厂商 LAB 阈值（`lab_config.yaml`）识别画面中出现的颜色与面积；不动车；结果需读出 |
| `robot_camera_snapshot` | 相机抓拍 | 感知/问答 | 无 | ✅ | ❌ | 抓一帧存为本地 JPEG 并返回路径；不动车；用于留档/排查画面 |
| `robot_arm_ik` | 机械臂坐标摆放 | 身体动作 | `x/y/z`（cm，安全盒）+ `pitch` | ✅ | ✅ | 逆运动学把末端摆到坐标（复用共享 board、不二次占用串口）；坐标自动限幅到安全盒，无解 `found=false`；**绝不动车轮** |
| `robot_face_enroll` | 人脸登记 | 感知/问答 | `name`（称呼，库内唯一）+ `id`（可选，留空自动生成 `p_xxxxxx`）+ `frames`（3~8，默认5） | ✅ | ✅（仅 s1/s3/s6 对准） | 引导式登记：当前画面无足够大正脸时先复用扫描+对准把脸摆正，再多帧采 SFace 嵌入写入派上 `faces.json`（**按 ID 存储**，每人最多 5 样本、近重复去重）；id/name 均全局查重（大小写不敏感），重复则拒绝；预览开着也可登记（自动借帧）；**绝不碰轮子** |
| `robot_face_recognize` | 人脸识别 | 感知/问答 | 无 | ✅ | ❌ | 只识人不扫描：当前画面取几帧 SFace 嵌入比对人脸库，多数表决返回 `person`（称呼）+ `person_id`（陌生/未匹配均 `null`）+ `distance`/`threshold`；不动车；结果需读出 |
| `robot_face_list` | 人脸库列表 | 感知/问答 | 无 | ✅ | ❌ | 列已登记成员（ID/称呼/样本数/登记时间）、当前阈值与**当前登录人**；纯 JSON 读取，不动相机不运动 |
| `robot_face_rename` | 人脸库编辑 | 感知/问答 | `key`（现有 ID/称呼）+ `id`（新 ID，可选）+ `name`（新称呼，可选） | ✅ | ❌ | 修改已登记成员的 ID/称呼（两者均可改）；新值全局查重，重复拒绝；登录态随 ID 迁移；纯 JSON 写入，不动车 |
| `robot_face_login` | 人脸登录 | 感知/问答 | 无 | ✅ | ❌ | 人脸识别登录：看当前画面识人（不扫描不转身），认出已登记成员则记为 `faces.json` 的"当前登录人"（face_list 可查）；**默认关闭**（需先打开开关 `robot.vision.faceLoginEnabled`，未开启时优雅返回"未开启"）；陌生/未登记脸登录失败；不动车 |

### 8.2 机械臂 pose 细分（`robot_arm_pose` 的 11 个语义动作）

| pose | 含义 | 实现方式 |
|---|---|---|
| `reset` | 归位站立 | 厂商动作组 `stand`（仅舵机） |
| `greet` / `thanks` | 打招呼 / 致谢 | 动作组 `Hiwonder` |
| `wave` | 挥手 | 动作组 `Hiwonder1` |
| `reach_left` / `reach_right` | 向前左/右伸手 | 动作组 `move_to_the_left_front` / `move_to_the_right_front` |
| `nod` | 点头 | 舵机往复微动作（id3, 600~800, 3 次） |
| `shake` | 摇头 | 厂商动作组 `shake_head`（9 帧完整编排，已替代旧舵机往复微动） |
| `bow` | 鞠躬 | 生成动作组 `bow`（头部深低 s3=500，均为厂商已用角度） |
| `raise_right` | 右手高举定格 | 生成动作组 `raise_right`（Hiwonder 里的举臂帧组合） |

### 8.3 动作后的语音反馈规则

为避免"动完还啰嗦一句"，注入大模型的工具被分为两类，收尾不同：

- **纯动作类**（`robot_arm_pose` / `robot_beep` / `robot_pick` / `robot_place` / `robot_play_music` / `robot_stop_music` / `robot_drive` / `robot_arm_ik` / `robot_set_rgb`）：动作本身即反馈，**成功后只补一句极短确认**（中文"好了"/日文"嗯，好了"/英文"Done."），**不再走二轮大模型自由播报**。
- **感知/问答类**（`robot_take_photo` / `robot_color_detect` / `robot_camera_snapshot` / `robot_search_face` / `robot_face_enroll` / `robot_face_recognize` / `robot_face_list` / `robot_face_rename` / `robot_face_login` / `robot_face_logout` / `robot_face_delete`，传感器查询 `robot_get_battery` / `robot_get_distance`，以及设备状态查询 `self_*`）：结果需要被"读出来"，**仍走二轮大模型正常作答**（search_face 命中时另由 server 按 `faceFound`/`faceFoundNamed` 固定文案播报带名结果，与二轮作答并存）。
- **失败一律照常播报原因**：工具报错、或设备回报业务失败（JSON `ok:false`，如未接线动作、被红线拒绝的 drive）时，不会假报"好了"，而由大模型说明做不到的原因。

> 判定实现：`core/services/llm.js`（function-call 循环短路与失败识别）+ `core/handlers/websocket.js`（动作集装配）。"纯动作类"集合从本节同源的动作目录派生（`category ∉ {vision, sensor}`，即传感/感知查询不入集、保留复述），不重复硬编码。

### 8.4 在设定页按需装载

设备「⚙ 设定」→ 机器人（function calling）区块有**装载动作类型**多选：

- 打开某台机器人型小智的设定 → 开关"是否为机器人"→ 出现按分类分组的动作勾选框（未接线/需放开红线项有标记）。
- **勾选=只把选中动作注入大模型**；未勾选的动作不会出现在可调用工具里（从源头收窄大模型能指挥的能力）。
- 支持"全选/清空"；全选≈默认的全部注入。
- 存储字段：`settings.robot.actions`（字符串数组，值取自 8.1 表 id）。
  - 未配置（旧设备）→ 保持"全部注入"的旧行为；
  - 空数组 → 不注入任何动作；
  - 具体子集 → 只注入该子集。
- 保存即时热推在线设备、持久化到设备库，重启不丢。

> 后端读写：`index.js` 的 `/api/settings/device`（含 `robot.actions` 校验，未知 id 直接 400）与 `/api/robot/action-types`（目录）；装载过滤：`core/handlers/websocket.js`。

### 8.5 与"一一对应绑定"的关系

动作装载是**在已绑定身体的前提下再收窄能力**：
1. `robot.body` 先决定"这台小智指挥哪个身体"（只注入该身体提供的工具）；
2. `robot.actions` 再决定"该身体的哪些动作类型装载给大模型"。

两者叠加：最终注入 = 绑定身体的工具 ∩ 勾选的动作类型（再受 `maxFunctions` 上限截断）。

## 9. HomeKit 配件配对排查

场景：Homecenter（`/firmware` 控制台 → 首页 → 局域网扫描 / 配对）扫描局域网内的 HomeKit 配件时，状态列有三种：

| 状态 | 含义 |
| --- | --- |
| 本机已配对 | 该配件已在本机 `data/homekit-pairing.json` 中有配对记录 |
| 可配对 | 配件 mDNS 广播带 `cf=1`，处于配对模式，可直接配对 |
| 已被其它控制端占用 | 配件广播中**没有** `cf=1`，即配件内部仍保存着一个有效的 HomeKit 配对 |

判定逻辑见 [`core/services/homekit.js`](../core/services/homekit.js) 的 `scan()`：状态直接透传配件 mDNS 的 `availableForPairing`（即 `cf` 标志），并叠加本机配对存储判断 `pairedHere`。

### 9.1 典型案例：Yeelight 灯泡 YLBulb1S(Dimmable)-6F3D

灯泡标签信息：型号 **YLDP15YL**（mDNS `md=YLDP15YL` 对应）、MAC **5C:50:C3:66:F3D** → 名称尾缀 **6F3D**、HomeKit 设置码 **1305-6827**。

在 Mac 上执行 mDNS 查询：

```sh
dns-sd -L "YLBulb1S(Dimmable)-6F3D" _hap._tcp local.
# ... md=YLDP15YL id=09:E5:F0:B7:0E:D8 sf=1 ff=1 ...   ← 没有 cf=1
```

TXT 记录里缺少 `cf=1`，说明灯泡本体仍带着一个有效的 HomeKit 配对，因此 Homecenter 标为"已被其它控制端占用"。而本机 `data/homekit-pairing.json` 只有 iHaper，说明**不是 Homecenter 自己占的**。

### 9.2 根因：从 iPhone 移除 ≠ 配件复位

HomeKit 的配对信息保存在**配件本体**上，而不是仅仅保存在手机上。只在 iPhone"家庭"App 里把配件移除，并不会清除配件内部的配对状态——很多单配对灯具（如 Yeelight）只要没做硬件复位，仍认为自己属于某个家庭，就不会再广播 `cf=1`。

此外，如果同一 iCloud 家庭下的其它设备（另一部 iPhone / iPad / HomePod / Apple TV）绑定过它，或它曾被米家 / Yeelight App 快捷配对，也会保持"已配对"状态。

### 9.3 解决步骤

**① 从所有 Apple 控制端移除**

- 家庭 App → 长按该配件 → 配件设置 → 底部**"移除配件"**（不是"从房间中移开"）。
- 检查同一 iCloud 家庭下的其它 iPhone / iPad / HomePod / Apple TV 是否也绑定过它。
- 曾被米家 / Yeelight App 快捷配对的，在其设置里一并解除。

**② 让配件回到 cf=1（分两种力度，优先用轻的）**

> ⚠️ 重要区分：Yeelight 灯泡的"断电→上电循环 5 次"是**整机恢复出厂**，会**连同 WiFi 配置一起抹掉**。复位后灯泡会退出路由器、掉出局域网，此时 Homecenter **根本扫描不到它**，必须先用 App 重新配网才能恢复。能不触发它就不要用它。

- **首选（保留 WiFi，灯泡留在局域网内）**：只在 iPhone"家庭"App 里对该配件执行步骤 ① 的"移除配件"。多数情况下移除后配件即重新广播 `cf=1`，无需任何硬件复位，直接回到步骤 ③ 配对即可。
- **兜底（会清 WiFi，需重新配网）**：仅当移除后仍显示"已被其它控制端占用"时，才做硬件复位：
  - **Yeelight 灯泡（YLDP15YL 等）**：断电 → 上电循环约 5 次（每次通/断约 2 秒），灯泡闪烁几下后稳定常亮即为复位完成。
  - **iHaper 等灯带控制器**：长按控制器配对键约 5 秒，或用电源通断复位（以厂商说明书为准）。

**②b 若做了 Yeelight 整机复位：先重新配回 WiFi（关键，否则扫不到）**

整机复位后灯泡已不在局域网，Homecenter 扫描不到属正常现象。恢复顺序：

1. 手机连上 2.4GHz WiFi，打开 **Yeelight App**（日本 Whitestone 版优先；或米家 App）→ 添加设备 → 按引导给灯泡重新配网，直到灯泡重新上线（路由器可分到 IP）。
2. 配网时若 App 询问"是否加入 Apple 家庭"：**想给 Homecenter 用就跳过 HomeKit 添加**（否则会被 iPhone 重新占用）。整机复位后的 HomeKit 出厂态，灯泡重新上线时会广播 `cf=1`。

**③ 回到 Homecenter 重新配对**

1. 点"🔍 扫描设备"，状态列变为橙色**"可配对"**。
2. 在左侧输入 HomeKit 设置码（如 `1305-6827`），点"🔗 配对"。
3. 若扫描后仍显示"已被其它控制端占用"，说明 HomeKit 未清干净，回到步骤 ②；若**完全扫描不到**，说明灯泡没连回 WiFi，回到步骤 ②b。

> 提示：`homekit.js` 的启动逻辑中，若 server 启动时已配置 pin 且发现 `cf=1` 的设备，会自动配对。因此复位后可直接在 Homecenter 页面点配对；即便被自动配走，也是配到本机，反而可用。

前端入口：Homecenter 扫描表格在"已被其它控制端占用"的行会显示"如何解除？"链接，点击弹出上述解除配对操作指引（见 [`studio/web/src/views/HomeView.vue`](../studio/web/src/views/HomeView.vue)）。

## 10. 常见故障排查

| 现象 | 根因 | 处理 |
|---|---|---|
| 卡"待命"、唤醒词完全无反应 | **烧错板型**：误用 `xingzhi-cube`（I2S 麦 GPIO5/6），本设备是 `luxiaoban`（PDM 麦 GPIO2/3）→ 麦全程无声 | 重烧正确板（见第 11 节）；判据：唤醒成功时串口会打印 `Encoded wake word into N packets` |
| 板子能开机但不联网、串口刷 `lamp_ble: adv report` | **烧进 BLE 探针固件**：构建目录沿用了 `sdkconfig.defaults.lampble` 覆盖层（NimBLE 中心设备容量探针，非语音固件） | 见第 11 节：按正常链重建，只重写 app 分区 |
| 提问后没回复、卡"倾听中" | ① aibridge 没起 → LLM `fetch failed`；② Edge TTS 偶发 429 限流 | 启动 aibridge；确认 3300 有响应；TTS 一般重试即恢复 |
| 设备离线、只发 OTA 不连 WebSocket | 旧版"断连式休眠"关掉整条 WS（已修）；或服务重启后设备未重连 | 唤醒一次设备重连；保持单进程运行服务器 |
| 8003 端口 LISTEN 但改动不生效 | 有旧 `run-server.js` 残留，设备连的是旧进程 | `pkill -f run-server.js` 后重启，用 `lsof -iTCP:8003 -sTCP:ESTABLISHED` 确认连接归属新 PID |
| 改了 `config.json` 没反应 | `ConfigLoader` 只在启动时读文件，`reloadConfig()` 无调用方（见 5.8.2） | 重启服务，或改走前台/API 写入 |
| 休息画面隔几分钟自己变回"聊天/待命" | 固件 120s 下行超时 + NAT 掐静默 TCP → 重连被判新会话 | 确认服务端 30s 心跳在跑（见 5.6），不要改固件定时器 |
| 设备端显示正常连着，后台「设备一览」却报未在线 / `/health` devices 恒 0 | 在线判定的旧活动窗口口径（见 5.7.6）；`/health` 的 Map 计数 | 已修；复核：`/api/voice/devices`（需 `X-Xiaozhi-Key`）与 `/api/devices/known`、`/health` 应同时报该设备在线，`lsof -iTCP:8003 -sTCP:ESTABLISHED` 有它的 IP |
| 唤醒后第一句先被补一句告别语 | 休息态无语音巡检未豁免（见 5.7.7） | 已修；需要更长的聊天态结束静默可调 `close_connection_no_voice_time` |
| 改了代码也重启了，界面还是离线 | 两种：① 旧进程 SIGTERM 退不干净，设备连在垂死进程上（见第 1 节）；② 设备一览**不轮询**，只在进页面/点⟳刷新时取数 | 按第 1 节流程验 PID 已消失；再点设备一览右上角「⟳ 刷新」（或直接比对 `/api/devices/known` 的 `online`）|
| 设备在线、TCP 也 ESTABLISHED，后台却显示离线 | 旧连接迟到 close 按 clientId 误删新登记（见 5.7.8） | 确认服务已加载 `activeConnections` 守卫；复核：`/api/voice/devices` 有它 = 登记正常，没有而 `lsof` 有连接 = 误删 |

## 11. 固件烧录要点（避免踩坑）

工程：`/Users/fengleiren/git/xiaozhi-esp32`（自有库 `xiaozhi-esp32-luxiaoban`，已与上游脱钩）。ESP-IDF v6.1（最低 v6.0.1，不支持 5.x）。

**每次 build / 烧录前，必须先核对板型**：
```
grep CONFIG_BOARD_TYPE sdkconfig
# 必须为：CONFIG_BOARD_TYPE_LUXIAOBAN_XIAOZHI_1_54TFT_WIFI=y
```
`sdkconfig` 被 gitignore、`idf.py build` 会静默沿用已选板型，改的是 board 无关代码（sleep / OTA）也别忘了核对。

编译 + 只烧应用（不动 bootloader/assets，快且安全）：
```
source /Users/fengleiren/esp/esp-idf/export.sh
idf.py build
python -m esptool --chip esp32s3 -p /dev/cu.usbmodem31101 -b 460800 \
  --before default-reset --after hard-reset write_flash 0x20000 build/xiaozhi.bin
```

**构建目录名不构成配置证据**（2026-10 实际踩坑）：仓库里留有 `build_lux` / `build_luxnospi` / `build_lichble` / `build_lichuang` 等历史目录，多数是别的实验的构建目录，直接复用会把不相关配置烧进板子。沿用任何目录前必须核 `CMakeCache.txt` 的 `SDKCONFIG_DEFAULTS` **完整链**，看链尾有没有 BLE 等实验覆盖层；链里没有板型文件（`sdkconfig.defaults.luxiaoban`）就是错的构建。

鹿小班正常构建链（8MB flash 实测，非参考文档写的 16MB）：
```
sdkconfig.defaults;sdkconfig.defaults.esp32s3;sdkconfig.defaults.luxiaoban;sdkconfig.defaults.luxiaoban8m
```
`sdkconfig.defaults.luxiaoban8m` 只做一件事：把 flash 布局退回 8MB（`partitions/v2/8m.csv`：ota_0/ota_1 各 0x2f0000、assets 2M @0x600000）且不引入 BLE。正常产物 app ≈ 2.88MB（分区余 6%）。

**恢复只烧坏板子的最小代价路径**（已验证，不动 NVS，WiFi 凭据保留）：
1. `esptool flash-id` 读实际容量；
2. 新配置干净构建，用**独立目录 + 独立 SDKCONFIG 文件**（`idf.py -B <新目录> -D SDKCONFIG=$PWD/sdkconfig.<变体> -D SDKCONFIG_DEFAULTS='<链>' set-target esp32s3`）；
3. 比对 `generated_assets.bin` 的 md5、`read_flash 0x8000 0xC00` 与产物分区表是否逐字节一致——一致则只重写 `0x20000` 的 app 即可，无需擦 assets/NVS。

**先确认板上镜像是否真的含本次源码改动**（不然改完固件代码看屏幕依旧错）：烧录时拷出的 `*_flashed.bin` 就是板上版本的时间戳，与源文件比即可判定：
```
stat -f "%Sm %N" -t "%F %T" main/application.cc main/display/lcd_display.cc build_*/*_flashed.bin
```
实例（2026-10-22）：鹿小班烧的是 10-21 18:04 的 `build_luxnospi/xiaozhi_flashed.bin`，而 `lcd_display.cc`（10-22 01:34）与 `application.cc`（10-22 12:56）在其后又被改过——即休息取图/`speaking` 豁免逻辑**不在板上**，屏幕行为与服务端口径不一致属预期，必须重编重烧。休息相关代码全在 `ShowStandby` 的取图优先级与 `HandleStateChangedEvent` 的休息标志清除条件上，这两处一动就得重烧才能验。

**读串口日志不要触发设备重启**：pyserial `open()` 默认会脉冲 DTR/RTS 复位一次，用 `s.dtr=False; s.rts=False` 后再 open，否则拿不到刚启动的日志。
